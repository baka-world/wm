# PR #18：冻结 V4 急诊调度的终端排队价值诊断（实际 CPU 实验）

> **结论：五步末端独立剩余工作量求和确实掩盖了任务执行顺序与后续资源排队；延长公有规则动力学预测后，旧失败案例的部分损失显著收窄。但这些收益 Rule 也获得了，未证明 V4 存在额外业务价值；计算成本大幅上升。**
>
> 所有实验是先前已查看的合成 Smoke/Development 场景，不是企业实测、独立测试或模型训练。

## 1. 原因与可复查的直接证据

冻结 H=5 的原有 `_projected_job_cost()` 将每个临床任务的乐观残余运输、服务时间相加，估计末端成本；`_route_remaining()` 没有完整模拟后续机器人任务顺序和共享工作站等待。在 **seed 904096、tick 76**，原 H=5 Rule 对三个不同的可执行任务分配给出完全相同的业务成本：急诊迟到 27.25，急诊剩余时间 15.25，常规迟到 0，常规剩余时间 172.75。V4 的小幅粒子预测波动却使首选翻转，导致那一次完整事实轨迹的常规流转恶化。

对原始归档可严格配对的多候选状态，Rule 的非索引业务成本完全相同者有 **42/297**（旧 stream）和 **27/164**（后续 keyed）；其中各有 3/10 和 11/21 个 V4 动作翻转出现在 Rule 完全打平状态。分母和轨迹不同，不可把这两个比率当作稳定性提升/恶化证明。

## 2. 实际实现和执行

- GitHub PR #18，在原分支新增可切换的 `--terminal-mode rule_continuation`，默认 `optimistic` 历史行为不变。
- 冻结 V4 checkpoint SHA-256：`60c8a6c3d832da3e6519072688ea099f64ae120ba19d3bd2ec705f7f1a11ac0c`；没有训练新模型或修改正式 CP-SAT、PIBT/LaCAM3。
- **两个方案的前 H=5 均维持原预测**：P4 为 Rule、P5 为 V4；两者统一使用 3 粒子和已经测试过的按服务会话键控的随机数。
- H=5 之后，**双方都改用现有 ProgressAwareRule + WorkflowDynamics 和相同 nearest 合法后续派单**，继续模拟公共资源容量及阶段释放直到已知工作流完成或仿真窗口截止，再按原任务级时效评分。这是队列敏感的确定性终端近似，不是多步 V4 网络预测，更不等于全局最优规划。
- 合法信息边界仍在：不读取隐藏复检结果、未来停机时间表、未公开任务、私有服务倒计时；模型不具备这些预测能力。
- [专用成功 CPU 工作流 #42985370778](https://github.com/lieuyimo/wm/actions/runs/42985370778)，[原始运行归档 #13839312037](https://github.com/lieuyimo/wm/actions/runs/42985370778/artifacts/13839312037)，包含已冻结的三个案例之逐候选评分、决策、任务指标、完整日志及 SHA-256。
- 4/4 自动测试通过；旧 `902147` 的 Rule/V4 原 `history_sha256` 均与之前归档严格相同。所有新场景均 0 容量/离散运动/生命周期违规；0 GPU、0 训练。

## 3. 三个已知场景的原始与新的真实仿真结果

只显示最直接的任务级指标。所有时间单位为 tick；未完成样本采用原受限流转定义。

| Seed | 方法 | H5 常规受限平均流转 | 延长终端后常规受限平均流转 | H5 急诊按时率 | 延长终端后急诊按时率 |
|---|---|---:|---:|---:|---:|
| 902147 | P4 Rule | 156.33 | **144.00** | 33.33% | 33.33% |
| 902147 | P5 V4 | 153.67 | **144.00** | 33.33% | 33.33% |
| 904096 | P4 Rule | 139.00 | **137.67** | 50.00% | 50.00% |
| 904096 | P5 V4 | 153.00 | **139.67** | 50.00% | 50.00% |
| 904388 | P4 Rule | 157.00 | **157.00** | 0% | 0% |
| 904388 | P5 V4 | 157.00 | **157.00** | 0% | 0% |

**904096**：在原键控 H5 对照中，V4 的常规受限流转比 Rule **多 14 tick/job**；新终端模式仍多 **2 tick/job**。从原先明显负收益收窄到小幅负收益。新的完整轨迹从 tick 0 起已有不同分配，不能声称这是单独修好了原 tick 76 的某一动作。

**902147**：延长终端后两种世界模型的完整事实轨迹一致，且常规任务受限流转都为 144 tick/job。新评分改善了两种方法，但没有 V4 的额外贡献。

**904388**：前后两个终端模式均未让急诊任务按时率改善，也没有常规任务级业务指标变化。延长终端后的 P4/P5 仍在 tick 97 有不同动作，未形成实际业务优势。

在三个已被选中的场景内，新模式 P4/V4 的急诊按时率均相同。**不能把同一批已观察故障的 3 个案例拿来声称独立统计提升。**

## 4. 性能成本

| 仅 3 场景全部策略 CPU 进程时间 | 原 H5 keyed | H5 + 规则终端继续模拟 |
|---|---:|---:|
| P4 Rule | 约 2.48 秒 | **约 35.21 秒** |
| P5 冻结 V4 | 约 3.48 秒 | **约 36.76 秒** |
| 两策略合计 | 约 5.97 秒 | **约 71.97 秒** |

新模式两臂总共新增约 **87,045 个**公开规则动力学终端预测步；V4 的神经查询仍只发生在前五步。主要成本来自延长规则预测，而不是重新训练模型。

从实时事件驱动调度需求看，完整终端连续模拟成本太高，更适合**离线参考或开发诊断**，不宜直接作为有限预算的在线默认策略。

## 5. 实际技术裁决

1. **实现 GO**：真实冻结 V4、急诊与动态复检、合法候选、长短两种终端预测都已跑通，原版本哈希回归通过。
2. **终端代理缺陷得到证据支持**：短 H5 下的乐观独立剩余工作量会对不同任务顺序打平；延长包含资源竞争的预测后，确实改变实际派单和业务结果。
3. **V4 独有调度增量仍未证明**：同等终端扩展下 Rule 也有可比改善；904096 常规流转仍比 Rule 多 2 tick/job，急诊按时率不变。
4. **在线性能 BLOCKED**：全流程继续预测的 CPU 成本约为原来的一个数量级，不能直接部署为默认滚动决策机制。
5. **不可扩大解释**：固定失败种子、合成数据、未建模的未来随机复检/到达/设备异常均限制因果与泛化结论。

**下一次真正值得开发的对象已经很具体：将规则终端继续预测中有用的资源竞争和任务顺序信息压缩成低成本终端价值近似；Rule 与 V4 必须使用相同近似和合法候选，并在新冻结开发场景上重新检验。不要继续通过增加网络复杂度或延长 V4 训练来补救评分器的业务目标错位。**
