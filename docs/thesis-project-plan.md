# 毕业设计实施主线

题目：《基于世界模型的样本转运调度系统设计与实现》。此文根据目前可见的交接内容和 2026-11-06 用户澄清整理；原分享对话可能未完整取得，具体业务规则和导师要求仍需以完整资料为准。下面的模块和顺序是实施草案，不代表它们已经开发完成。

## 目标

围绕实验室样本转运，在仿真环境中设计并实现一个可运行的调度系统：表达样本运输任务、机器人和站点状态；生成可执行的调度方案；使用世界模型预测候选方案的后续状态或风险；执行仿真并记录结果；在毕业论文中说明需求、设计、实现和测试。

世界模型应有明确的预测职责，而不只是保存当前状态。模型的具体形式、是否训练轻量模型、预测范围及评价方式，要结合可用数据和毕业设计要求确定。创新点和论文对照可以归纳实际工作，但不以先声称新算法为系统实施前提，也不预设模型必定优于传统方法。

## 已知边界和当前进展

- 已知约束：CPU 执行，不使用 GPU 或付费云资源，不修改上游项目；优先在功能分支和 PR 工作，未经用户确认不合并。
- RGTA 的小规模测试已通过。Lay2Graph 在上游仓储场景中完成了两台机器人和 6 个订单的仿真闭环，日志见 `docs/framework-assessment.md`。这些是基础框架验收，不是实验室样本转运系统已完成。
- 已新增独立的 CPU 样本转运原型：示例地图、机器人、样本任务、传统与预测调度、离线回放及自动测试。世界模型目前是基于已观测站点服务时长和静态路径的可解释预测基线，尚不是神经网络，也尚未接入 Lay2Graph。运行方式与限制见 `docs/prototype.md`。
- 样本类型、站点布局、任务规则、界面范围、具体世界模型形式和导师对论文的要求，目前不能从现有资料完整确定。实施时应将假设写明，避免把候选设计当成既定需求。

## 候选系统结构

1. **样本与运输任务**：表达待转运样本、起点与目标站点、任务状态和必要时间信息；具体字段按业务资料确定。
2. **仿真环境与状态**：表示地图、站点和机器人，推进任务执行并记录状态变化；评估使用 Lay2Graph 作为仿真基础的适配成本，也保留其他轻量方案。
3. **调度与路径**：形成满足已建模约束的候选任务分配及路线，并在状态变化时处理重新调度。使用传统调度作为可运行的基础方案。
4. **世界模型预测**：输入当前机器人、任务与站点状态以及候选调度动作，预测一定时间内可能出现的状态、延迟或资源占用；输出供调度选择和结果分析使用。预测方法及可靠性处理仍需设计与验证。
5. **运行记录与结果展示**：保存任务、机器人和预测/调度结果，使系统演示与测试可复现；是否需要图形界面及其范围待结合论文要求确定。

示意流程：任务进入 → 获取环境状态 → 生成可行候选方案 → 世界模型预测候选结果 → 选择并执行方案 → 更新状态与记录。碰撞及容量等约束以实际实现和测试证据为准，不能仅因架构图而宣称得到保障。

## 建议推进顺序

1. 根据现有业务资料建立最小实验室地图和样本转运场景，明确任务、机器人、站点及其状态；先实现可运行的基础转运闭环。
2. 明确系统模块与数据接口，决定如何复用或适配已验收的框架；保持上游代码不变，并在本仓库维护适配代码和可复现配置。
3. 在基础调度上接入世界模型预测，说明输入、输出、训练或规则来源及使用方式；必要时用 CPU 可运行的轻量方法实现。
4. 通过正常任务及合理的延迟、阻塞等场景测试功能、调度结果和系统开销；使用合适基线，如实记录结果与限制。
5. 随实现整理论文材料：绪论与相关工作、需求分析、总体设计、关键模块实现、实验与测试、总结。章节安排可按学校或导师模板调整。

文献和创新空间调查已保存在 `docs/related-work-and-stage-zero.md`，作为背景资料使用。最小场景和基础原型已经建立；下一步是结合实际实验室和论文要求细化场景、世界模型形式与系统接口，并扩展测试和论文材料。
