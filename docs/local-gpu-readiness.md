# 本地 GPU 接入：现状、准备工作和分工

## 目标和边界

GitHub Actions 用于复现和测试；后续计划由用户自己的本地 GPU 运行模型。当前开发和 CI 只使用 CPU，不启用付费云资源或云端 GPU，不修改上游项目，未经用户确认不合并 PR。用户希望集中处理模型内容；场景、数据、框架、脚本、验收与自动化由项目执行方准备。

尚不知道本地设备的 GPU 型号、显存、系统、驱动及连接方式。历史对话中提及的 V100 16 GB 只是线索，不能当作已核实的设备。[PR #2](https://github.com/lieuyimo/wm/pull/2) 已并入其基础分支，[PR #1](https://github.com/lieuyimo/wm/pull/1) 已并入 `main`；本地可从默认分支开始，具体拉取和验证步骤见[开发指南](local-development.md)。

## 目前完成的基础

| 事项 | 现状 | 剩余工作 |
| --- | --- | --- |
| 场景与仿真 | 两张有来源的公开导航地图、多机器人任务、状态记录和外部分配回调可用 | 实验任务与站点角色仍是明确标注的合成假设；真实 SOP、容量及更多扰动需证据后再加入 |
| 数据 | 可从固定来源生成按场次、地图及任务时间表划分的可观测轨迹，校验文件、分组、时间边界和离散移动 | 现有是小规模仿真数据；序列窗口训练、新地图导入和跨独立数据集去重尚未完成 |
| 可替换模型 | 数据、批次、损失、模型和 `predict_next` 有适配接口；提供 PyTorch 小网络作为流程验证示例 | 示例不是最终论文模型；目前的张量批次结构和优化器可满足示例，复杂图模型或层次模型可能需扩展 |
| 本地训练入口 | 支持明确选择 CPU/CUDA、训练、验证集选轮次、模型与优化器检查点、同环境断点恢复及设备记录 | CPU 路径已有实际验收；CUDA 构建、显存和恢复还没有在用户的 GPU 实测 |
| 评估与闭环 | 固定检查点可在留出轨迹上与规则预测对比单步和有限条件的多步预测，也可注入仿真器，对有预算的候选动作做预测与分配 | 目前是验证模型和接口的闭环，不是完整的等预算调度实验；外生事件预测、可信度及恢复策略仍需研究与完善 |
| CI | 工作流安装 CPU 版 PyTorch，运行数据、无未来信息泄漏、批处理、恢复、回退、留出评估和多机器人仿真测试 | 不测本地 CUDA、真实机器人或物理安全 |

固定地图完整数据生成入口见 [PyTorch 训练说明](pytorch-training.md)。此前已实际生成并校验 96 场、21,269 条转移：训练 48 场 / 11,848 条，验证 16 场 / 3,988 条，医院测试 16 场 / 3,904 条，诊所测试 16 场 / 1,529 条；约 76 MiB。它们只存在运行目录，未上传。训练/验证/测试的任务时间表无跨组重复；每场最后 `end_of_run` 转移未导出。

示例神经网络可以在 CPU 上完成训练、读取检查点并驱动真实仿真循环；对完整训练集训练一轮后，两个完整留出集的预测结果仍落后于规则参考。逐场结果与边界见 [验收记录](pytorch-smoke-acceptance.md)；它们不是调参结果或最终论文结论。原有纯 Python 线性状态模型仍是独立基线，并不是 CUDA 网络。

## 哪些工作需要用户介入

- **模型方向**：执行方先给出可审阅的状态、动作、输出、训练目标和备选网络；用户可决定论文模型。已核实交接材料没有此前“分层模型”的完整结构，目前示例不应冒充该结构。如果模型已由导师或之前的材料规定，需要相应资料来准确实现；没有时可继续完善通用框架。
- **实际连接本地 GPU**：当设备可接入并授权时，执行方检查驱动、PyTorch、显存和路径，运行训练、恢复与评估；若无法直接访问，只需用户运行准备好的少量命令并返回文本结果，不要求截图或让用户自己改框架。只有实际在该设备执行后才能确认 GPU 可用性、峰值显存和稳定性。
- **只有用户能确定的业务与论文要求**：如导师指定的样本范围、实验场所资料、论文格式。没有来源时保留仿真假设，不编造临床规则。

## 进入正式实验前还需确认

1. 对拟定的最终模型落实具体输入、输出、损失、模型版本与数据窗口。小型单步网络只是可替换的接口示例，不能直接等同于完整世界模型。
2. 接入实际 GPU，完成一次明确显示 CUDA 设备的前向、反向、检查点保存与恢复，记录软件环境和显存；若训练规模较大，还需测试完整数据吞吐、长任务稳定性与资源占用。
3. 在独立场景中制定公平的规则/学习基线、预算和指标，分别报告预测准确性与调度效果；测试集不得用于挑选参数。当前示例网络和一次闭环成功无法证明优于传统方法。
4. 继续完善任务/站点资源约束、可解释的异常来源、失败恢复和复现实验；真实部署或临床适用性不在当前仿真验收范围内。
